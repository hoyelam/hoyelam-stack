# Orchestrate Project

The lead owns the outcome: frame the work, delegate substantial independent units, resolve decisions and dependencies, inspect results, and verify their integration. Keep useful lead work moving while workers execute. Work directly when delegation adds no value or the remaining work is tightly coupled.

## Choose tools and records

Use available delegation through [single-task delegation](../hoyelam-mode/references/single-task-delegation.md), honoring explicit execution preferences. Choose concurrency from ready independent work, exclusive resources, and actual runtime capacity. Keep one lead accountable across execution routes; add another coordination layer only when it solves a real management bottleneck.

Use one authoritative record: existing project tools or a small task-owned file can suffice. Preserve the goal, units and dependencies, owners, relevant instructions, current results and artifacts, acceptance evidence, and unresolved decisions. Add session identities, attempts, and durable ownership records when retries, concurrent writers, or interruption require them. Keep scratch records out of commits unless requested.

Select the [bundled runtime](references/bundled-runtime.md) when automated assignment identity, exclusive scope leases, inbox handling, or recovery materially helps. It is optional; read its command contract only when selected. No particular model, hosting service, PR tool, or CI service is required.

## Coordinate execution

1. **Frame and brief.** Define observable success, independently writable units, and required unit and integration checks before assigning work. Give workers the relevant discovered context, authority, ownership boundary, acceptance criteria, and evidence expectations; use the [compact brief](references/worker-brief.md) when useful. Relay actual dependency outputs. Preserve one writer per mutable boundary, including shared files, branches, worktrees, simulators, and accounts.
2. **Delegate ready work.** Start independent units whose prerequisite evidence is current. Pilot a representative unit first only when uncertainty in a repeated method or verification recipe could change later assignments; otherwise fan out ready work. Refill capacity as results arrive. If delegation is unavailable, execute sequentially and report that limit.
3. **Assess and resolve.** At safe boundaries, inspect actual changes and evidence, reconcile reports with their assignments, and distinguish success, failure, blockers, cancellation, and stale attempts. Use independent review for substantial or risky changes when available. Apply `$prove-the-work` and `$review-and-resolve` as needed: fix confirmed in-scope issues, preserve failure evidence, and rerun affected checks. Worker completion and review assertions are evidence to assess, not acceptance by themselves.
4. **Integrate and prove.** Integrate accepted units as dependencies permit, with one owner of the integration branch. Identify the combined artifact, including uncommitted changes, and run the selected integration checks; passing units alone cannot prove their composition. Restacks, conflict fixes, and later edits require affected checks again. Publishing, landing, deployment, and external messages require authority beyond implementation alone.

## Evidence and recovery

Bind results to the tested artifact and relevant configuration or fixtures. Record the check or interaction, expected and observed outcome, counts and exit status where applicable, and useful artifact paths. Runtime evidence identifies the application instance, exercised user path, and resulting state; readiness alone does not prove behavior. Retain unaffected evidence only when its claims remain current.

On resume or reassignment, reconcile records with live workers, worktrees, ownership, attempts, dependencies, and artifacts before starting more writes. Accept a late result only if it still matches the assignment and current dependencies. Release ownership before reassignment and preserve useful findings from stale work. Diagnose failures before retrying, use a finite budget suited to the cause, and continue independent work around blockers. Restore or reconcile corrupt records before they govern new assignments.

Completion requires the original outcome and required checks on the integrated final state, resolved in-scope findings, and accounted-for assignments and ownership. Report failed or blocked checks and the next action honestly. Abandoning a required unit does not satisfy the goal; closing bookkeeping does not establish completion.
